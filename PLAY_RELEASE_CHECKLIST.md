# Google Play release checklist — v1

Status as of 2026-09-06. This file is the pick-up point for the Play submission work.
It records decisions already made, what is finished, and what is left.

## Scope decision for v1

**v1 ships offline-only.** Play AI, Pass & Play, Watch AI and the tutorial all work with no
server, no login and no internet. Online multiplayer is deferred to v2.

Reasoning: online is the only feature that drags in a hosted backend, an account-deletion
flow, detailed Data Safety disclosures and running cost. Removing it from v1 scope cuts
weeks off the path to a submittable build and costs nothing, because the offline modes are
already complete and tested.

**Bluetooth / local multiplayer is deferred to v2 as well.** It was assessed and is a
structural change, not a transport swap: the architecture is server-authoritative, so the
host phone would have to become the authority, meaning `server/game-service.js`,
`game/engine.js` and `game/ai.js` would need porting into the WebView, giving a third
implementation of the rules to keep in parity. On top of that: a native RFCOMM layer,
runtime Bluetooth permissions (the app currently requests none), a bidirectional JS bridge,
a separate lobby flow, and testing that is entirely manual across two or more devices.
Estimated larger than every other outstanding v1 item combined. If local multiplayer is
built later, evaluate **Nearby Connections** rather than raw Bluetooth: it covers Bluetooth
and Wi-Fi Direct together with far less native code, at the cost of a Google Play Services
dependency.

## Open decision — carried forward

**Hide "Play Online" in release builds?**

Not yet done. Currently the signed release build still shows the **Play Online** button.
Because `SERVER_BASE_URL` is empty, tapping it opens the lobby and asks the user to type a
server address.

Three reasons to gate it for v1:

1. Play review risk — a prominent feature that cannot function is a common rejection reason.
2. User confusion — asking a consumer for a "server address" is a developer-facing UI.
3. Data Safety — with online unreachable, the form is a clean "no data collected".

Proposed implementation: extend the existing `release=1` block at
`House_of_Kiran_AI_Stage3_6_PRODUCTION.html:3672`, which already removes the developer menu
in release builds. Roughly three lines, using a pattern already proven on device.

This deletes nothing. The lobby, server and account code all remain; the debug build keeps
online for LAN testing; re-enabling for v2 is a one-line change.

## Known issues not blocking v1

These matter only when online multiplayer ships in v2:

- `server/rate-limit.js` keys on `request.socket.remoteAddress`. Behind a reverse proxy every
  player shares one bucket. Must be fixed before any public deployment.
- `games`, `players` and `commands` rows are never expired, so storage grows without bound.
- No account deletion endpoint or UI. Google Play requires one for apps offering account
  creation, so this is a hard blocker for a v2 that ships online.
